# T10 批准 C 材料：G-BASE 资源与基线预算（2026-11-09）

这份材料供研究者审阅签署。批准 A、B 已签，两个 smoke 都 PASS（见 `gpu_measurement_isles_u.md`、`gpu_measurement_skm_a.md`）。G-BASE 预评估中，两个 scope 的五项证据都是 PASS，唯一的阻断项是 `APPROVAL_MISSING:resources`，也就是这里的 C。

- 批准文件由研究者本人写入服务器私有根下的 `approvals/` 子目录（目录 700，文件 600）。代理不代填 `approved_by`，也不代写任何批准文件。
- 下文用 `$V` 表示私有根，`$R` 表示原始数据根。两者的实际值只写在服务器本地，不进仓库。
- 已有的“同时最多 2 张空闲 GPU”授权只是数量上限。基线配方是否批准，以这里的 C 为准。
- 科学结论：NOT_EVALUATED。基线只给出开发集描述，不做 locked_test 评价，不形成正式阈值。

## 1. 待签文件

- 文件：`$V/approvals/gbase_resources_20261109.yaml`。日期可以改，执行命令时按实际文件名填写。
- 按关卡分键，与 `configs/v5/approvals.template.yaml` 一致。smoke 用的 `resources` 不在 G-BASE 键下，所以不会打开 G-BASE。
- 签署的对象是对应基线计划文件的全部内容，由 sha256 绑定：
  - 计划改动任何一处，sha256 都会变，需要重新签；
  - 注释不计入哈希。
- 基线驱动在读取任何数据之前做三项检查：
  - 文件里有没有本 scope 的 G-BASE `resources`；
  - 其中的 `baseline_plan_sha256` 是否等于计划的哈希；
  - 签名是不是测试用的占位签名。

  任何一项不符，驱动就拒绝运行，也不建输出目录。

```yaml
isles_u:
  G-BASE-U:
    resources:
      approved_by: <研究者本人填写>
      approved_at: <YYYY-MM-DD>

      baseline_plan_sha256: 96040004dd1afce9a10c79e30b308fa49d47654b67205151412bf0479b96b8de
skm_a:

      scope_hash: c70f7dca4c94ea4454ce0a41794d931a2a81fb27db1e605b18ca24e98f85bfd7
```

## 2. 两个基线计划（提案，待审阅）

计划文件：`configs/v5/proposals/baseline_isles_u.yaml`、`configs/v5/proposals/baseline_skm_a.yaml`。

**与 smoke 的关系：**
- 配方就是已通过的 smoke 配方，加上 smoke 按规则选中的候选。以下各项与 smoke 完全相同：模型、种子、优化器、调度、输入政策、采样、推理窗口、监督政策、接受政策。
- 只有四项允许不同：配方 id、可读角色、步数与墙钟预算、检查点间隔。
- 驱动和测试都会逐项核对上述关系。
- 计划还记录了所依据的 smoke 计划 sha256，以及 smoke 报告的 sha256。后者与仓库中的 `gpu_measurement_<scope>.md` 逐字节一致。

**不在 C 的范围内：**
- 正式阈值、容差或临床判定；
- locked_test 评价；
- 联合 SKM 训练（T11）；
- 任何预训练或微调。

**停止规则：**
- 训练中出现 OOM、非有限值或训练墙钟超限，基线就停在训练阶段，写入 failure 记录，不重试；
- 训练结束后、每例开发推理之前都检查整体预算，超限就报 `BASELINE_BUDGET_EXCEEDED` 并停止，不出部分结果；
- 不为得到某个数值修改计划。改计划就要换新哈希、重新签署。

**两个基线分开训练、分开评估、分开报告，结果不相加。**

## 3. 签署后的执行顺序

服务器上每一步都使用以下环境：

```sh
export PYTHONNOUSERSITE=1 PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=. CUBLAS_WORKSPACE_CONFIG=:4096:8
umask 077
```

GPU 步骤另设 `CUDA_VISIBLE_DEVICES=<确认空闲的 1 张卡>`。

1. **同步代码并核对哈希。** 用 bundle 把代码同步到包含本材料的提交，在服务器上用 CPU 跑全套测试。再确认两个计划的 sha256 与第 1 节一致：

   ```sh
   python -m anatobind.v41.real_baseline_v5 plan-hash --plan configs/v5/proposals/baseline_isles_u.yaml \
     --smoke-plan configs/v5/proposals/smoke_isles_u.yaml --scope configs/v5/scope_isles_u.yaml \
     --policies configs/v5/sources_v5.yaml --source-id isles_2022
   ```

   skm_a 同样执行一次，替换为 `baseline_skm_a.yaml`、`smoke_skm_a.yaml`、`scope_skm_a.yaml` 和 `--source-id skm_tea`。

2. **G-BASE 关卡**，两个 scope 各执行一次，输出到新目录：

   ```sh
   python -m anatobind.v41.real_t10_v5 gbase-gate --plan configs/v5/proposals/smoke_isles_u.yaml \
     --scope configs/v5/scope_isles_u.yaml --policies configs/v5/sources_v5.yaml --source-id isles_2022 \
     --gdata-decision $V/t10/gdata_gate_isles_u/gdata_decision.json \
     --split-summary $V/t08/isles_u/split_summary.json \
     --smoke-evidence $V/t10/smoke_isles_u_r2/training_smoke_evidence.json \
     --approvals $V/approvals/gbase_resources_20261109.yaml --out $V/t10/gbase_gate_isles_u
   ```

   skm_a 对应 G-BASE-A，替换以下参数：

   | 参数 | 值 |
   | --- | --- |
   | `--plan` | `smoke_skm_a.yaml` |
   | `--scope` | `scope_skm_a.yaml` |
   | `--source-id` | `skm_tea` |
   | `--gdata-decision` | `$V/t10/gdata_gate_skm_a/…` |
   | `--split-summary` | `$V/t08/skm_a/…` |
   | `--smoke-evidence` | `$V/t10/smoke_skm_a/…` |
   | `--out` | `$V/t10/gbase_gate_skm_a` |

   不是 PASS 就停在这一步，报告阻断项。

3. **基线 isles_u**（1 张卡）：

   ```sh
   python -m anatobind.v41.real_baseline_v5 baseline --plan configs/v5/proposals/baseline_isles_u.yaml \
     --smoke-plan configs/v5/proposals/smoke_isles_u.yaml --scope configs/v5/scope_isles_u.yaml \
     --policies configs/v5/sources_v5.yaml --source-id isles_2022 --raw $R \
     --records $V/t07/isles_migrate/records_v5.jsonl --split-registry $V/t08/isles_u/split_registry.json \
     --gbase-decision $V/t10/gbase_gate_isles_u/gbase_decision.json \
     --smoke-evidence $V/t10/smoke_isles_u_r2/training_smoke_evidence.json \
     --approvals $V/approvals/gbase_resources_20261109.yaml --run-id baseline_isles_u_v1 --device cuda:0 \
     --out $V/t10/baseline_isles_u
   ```

4. **基线 skm_a**（另 1 张卡）：
   - 在 isles_u 写出第一个检查点后启动。同时最多占 2 张卡，在已授权的数量上限内。
   - 参数按第 2 步的方式替换为 skm_a 的文件，另外：
     - `--records $V/t07/skm_migrate/records_v5.jsonl`
     - `--run-id baseline_skm_a_v1`
     - `--out $V/t10/baseline_skm_a`

5. **结果入库。**
   - 每个基线的私有输出目录里会生成 `module_baseline.md`。先人工复核它是否脱敏，再复制为 `reports/v5/module_baseline_<scope>.md`，并加入脱敏测试。
   - 两份报告都入库后，T10 的 `data_run_status` 才改为 PASS。
   - 如果失败，诊断原因并保留全部记录，然后报告；不修改标准，不自动重跑。

- 两个基线分开报告；`scientific_conclusion` 保持 NOT_EVALUATED；`core_target_validated` 保持 null。
